# Руководство для контрибьюторов

Спасибо, что решили внести свой вклад в LANdapter! Мы рады любым улучшениям — от исправления опечаток до новых функций.

В этом документе описаны правила и рекомендации, которые помогут сделать ваш вклад максимально полезным и упростят процесс ревью.

---

## Сообщение об ошибках

Если вы нашли ошибку или что-то работает не так, как ожидалось, пожалуйста, создайте **Issue** в GitHub.

**Перед созданием Issue:**
- Проверьте, нет ли уже похожего отчёта (используйте поиск).
- Убедитесь, что вы используете последнюю версию (main-ветку).

**В описании укажите:**
- Версию Go, PostgreSQL, Node.js.
- Операционную систему и её версию.
- Краткое описание проблемы.
- Шаги для воспроизведения.
- Ожидаемое и фактическое поведение.
- Логи (если есть) и скриншоты (для фронтенд-ошибок).

Шаблон для Issue можно найти в `.github/ISSUE_TEMPLATE.md` (если он есть).

---

## Предложения новых функций

Мы открыты к новым идеям! Прежде чем начать разработку, создайте Issue с меткой `enhancement` и опишите:

- Какую проблему решает функция.
- Предлагаемое решение (можно схематично).
- Альтернативы (если есть).

Это позволит обсудить идею и избежать ситуации, когда вы сделаете большую работу, а она не будет принята.

## Процесс разработки

### 1. Форк репозитория

Сделайте форк проекта в свой аккаунт GitHub и клонируйте его локально.

```bash
git clone git@github.com:chocom1nt/LANdapter.git
cd LANdapter
```

### 2. Создание ветки

Создайте ветку для вашей работы. Название должно отражать суть изменений:

- `fix/short-description` – для исправлений ошибок.
- `feature/feature-name` – для новых функций.
- `docs/change` – для документации.

```bash
git checkout -b feature/awesome-new-feature
```

### 3. Разработка

Пишите код, следуя правилам стиля (см. ниже). Не забывайте о тестах!

#### Структура проекта

Основные папки:

- `cmd/` – точки входа (master, agent).
- `internal/` – внутренняя логика (не импортируется извне).
- `storage/` – слой данных (интерфейсы и реализация для PostgreSQL).
- `web/` – React-фронтенд.
- `migrations/` – SQL-миграции.
- `docs/` – документация.

Подробнее о структуре см. в `ARCHITECTURE.md`.

### 4. Коммиты

Пишите осмысленные сообщения коммитов. Рекомендуем использовать [Conventional Commits](https://www.conventionalcommits.org/):

- `feat: add support for Linux ARM64`
- `fix: prevent panic when upload dir is missing`
- `docs: update API reference`
- `test: add unit tests for installer`

Это помогает автоматически генерировать Changelog.

### 5. Тестирование

**Запуск всех тестов:**

```bash
make test
```

**Только юнит-тесты:**

```bash
make test-unit
```

**Интеграционные тесты (требуют реальную PostgreSQL):**

```bash
make test-integration
```

**Проверка покрытия:**

```bash
make test-cover
```

Если вы добавляете новую функциональность, обязательно напишите тесты для неё. Это обязательное требование для принятия PR.

### 6. Линтинг

Перед отправкой PR убедитесь, что код проходит проверку линтерами.

**Для Go:**

```bash
golangci-lint run ./...
```

(Если у вас не установлен `golangci-lint`, установите согласно [инструкции](https://golangci-lint.run/usage/install/).)

**Для фронтенда (в папке `web/`):**

```bash
npm run lint   # если добавите ESLint
```

На данный момент фронтенд не имеет строгих линтеров, но мы рекомендуем придерживаться стиля, используемого в существующих файлах.

### 7. Форматирование

**Go:** используйте `gofmt` (или `goimports`). Можно настроить автоматическое форматирование в редакторе.

```bash
go fmt ./...
```

**React:** в IDE можно настроить Prettier.

### 8. Сборка и ручное тестирование

Убедитесь, что проект собирается и запускается без ошибок:

```bash
make build
make run-master   # в одном терминале
make run-agent    # в другом
```

Проверьте, что ваши изменения не сломали существующие функции.

### 9. Создание Pull Request

Когда работа готова, отправьте её в ваш форк и создайте Pull Request в `main`-ветку оригинального репозитория.

**В описании PR укажите:**

- Ссылку на Issue (если есть).
- Краткое описание изменений.
- Как проверить (если нужно).
- Скриншоты для UI-изменений.

**Пример описания:**

> Closes #42  
> Добавлена поддержка удалённого выполнения команд через WebSocket.  
> Для проверки: запустите агента, отправьте команду `stats` через API `/api/v1/clients/{id}/stats`.

## Стиль кода

### Go

- Используйте `gofmt` (обязательно).
- Имена переменных: camelCase, но с учётом правил экспорта (экспортируемые — с большой буквы).
- Обрабатывайте все ошибки явно (`if err != nil`).
- Старайтесь избегать глобальных переменных, используйте внедрение зависимостей.
- Документируйте публичные функции и типы (в формате godoc).

### React / JavaScript

- Используйте функциональные компоненты и хуки.
- Имена файлов: `PascalCase.jsx` для компонентов, `camelCase.js` для утилит.
- Старайтесь избегать inline-стилей, используйте Tailwind CSS.
- Компоненты должны быть небольшими и переиспользуемыми.

## Документация

Любое изменение API, конфигурации или добавление новой функции должно сопровождаться обновлением документации в папке `docs/`.

- API-эндпоинты описывайте в `README.API.md`.
- Параметры конфигурации — в `CONFIG.md`.
- Новые идеи и архитектура — в `ARCHITECTURE.md`.

---

## Процесс ревью

После создания PR мы постараемся ответить в течение нескольких дней. Во время ревью могут быть замечания и просьбы что-то поправить. Пожалуйста, относитесь к этому конструктивно.

После одобрения PR будет слит в основную ветку.

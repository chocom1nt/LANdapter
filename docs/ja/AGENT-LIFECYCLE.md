# Agent のライフサイクル、登録、サービス運用

現在の Agent の動作、認証情報を明示的に発行する理由、無人ワークステーション展開の推奨方式を説明します。

## 現在の動作

- `make run-agent` または `go run ./cmd/agent` で起動すると、Agent はフォアグラウンドプロセスとして動作します。リポジトリには Windows サービス用インストーラーや systemd unit はまだ含まれていません。
- Agent は WebSocket で Master に接続し、切断後に再接続します。Master は PostgreSQL に保存された Agent トークンのハッシュで認証します。
- 接続時に Agent は ID と基本的なホスト情報を送信します。デバイス一覧と CPU/RAM/uptime は Web UI/TUI から必要時に取得されます。継続的なテレメトリ送信と自動アラートは未実装です。
- 各 Agent には `configs/agent.yaml` または `AGENT_UUID` / `AGENT_TOKEN` 環境変数で固有の `uuid` と `token` が必要です。環境変数は YAML より優先されます。

## なぜ全クライアントへ自動的にトークンを発行しないのですか？

接続してきた任意の端末に恒久的な認証情報を発行すると、ネットワーク上の未許可端末が登録され、リモートインストール命令を受け取る可能性があります。現在の登録 API は管理者トークンで保護されているため、Agent は承認済みの登録シークレットなしでは安全に登録できません。Agent ごとのトークンなら個別に失効・ローテーションできます。

## 推奨する無人登録方式

1. 管理者が環境やグループに限定した、短時間で失効する一回限りの登録コードまたは展開パッケージを作成します。
2. Agent インストーラーには、MDM、構成管理、保護された共有領域などの安全な経路で登録シークレットを渡します。公開 URL やソースコードには埋め込みません。
3. Agent は登録シークレットを固有の Agent 認証情報に交換します。Master はハッシュのみ保存し、平文トークンは一度だけ返して、ローカルで厳格なアクセス権限の下に保存します。
4. ポリシーに応じて自動承認するか、管理者の承認待ちにします。登録コードには有効期限と使用回数制限を設け、失効できるようにします。
5. Agent は自動起動と障害時再起動を備えた Windows サービスまたは systemd サービスとして導入し、可能なら最小権限の専用アカウントと集中ログを使用します。

## 現在の Agent をバックグラウンドで動かす

ネイティブのサービスインストーラーが追加されるまでは、組織で承認されたサービス管理ツールや展開ツールを使用してください。Linux では固定の作業ディレクトリ、制限された設定ファイル権限、`restart-on-failure`、専用アカウントを持つ systemd unit を推奨します。Windows では承認済みのサービスラッパーを使うか、ネイティブサービスとしてパッケージ化してください。`configs/agent.yaml` を保護し、本番トークンを Git、公開インストーラー引数、スクリーンショット、ログに含めないでください。対話型インストーラーは別途検証してください。バックグラウンドサービスはログオンユーザーのデスクトップにアクセスできない場合があります。

## 現在の制限と今後の計画

- 事前に Agent トークンを配布しない自動登録は未実装です。
- Windows サービスと systemd unit のネイティブインストールは未提供です。
- 継続的なテレメトリ、イベント転送、アラートルール、管理者通知は未実装です。現在の UI は必要時にメトリクスを要求します。
- 将来の登録フローでは、期限付き一回限りの bootstrap 資格情報、Agent ごとの ID、承認制御、レート制限、TLS/WSS、監査ログを使用するべきです。

# Жизненный цикл агента, регистрация и работа службой

Здесь описано текущее поведение Agent, зачем выдаются отдельные учётные данные и как лучше организовать автономное развёртывание рабочих станций.

## Как работает сейчас

- При запуске через `make run-agent` или `go run ./cmd/agent` агент работает как процесс в текущем терминале. В репозитории пока нет встроенного установщика службы Windows или готового systemd unit.
- Агент подключается к Master по WebSocket и переподключается после потери соединения. Master проверяет токен агента по хешу, сохранённому в PostgreSQL.
- При подключении агент передаёт идентификатор и базовую информацию о компьютере. Инвентарь устройств и показатели CPU/RAM/uptime запрашиваются веб-интерфейсом и TUI по требованию; постоянная передача метрик и проактивные оповещения пока не реализованы.
- Для каждого агента нужны собственные `uuid` и `token` в `configs/agent.yaml` либо переменные `AGENT_UUID` и `AGENT_TOKEN`. Переменные окружения имеют приоритет над YAML.

## Почему нельзя автоматически выдавать токен любому клиенту?

Если Master выдаёт постоянные учётные данные любой машине, которая подключилась, посторонний компьютер в сети сможет зарегистрироваться и потенциально получать команды удалённой установки. Текущий endpoint регистрации защищён административным токеном; агент не может безопасно вызвать его без уже выданного секрета. Отдельные токены также позволяют отозвать или заменить доступ только одного агента.

## Рекомендуемая схема автономной регистрации

1. Администратор создаёт временный одноразовый код регистрации или пакет развёртывания, ограниченный средой/группой.
2. Установщик агента получает секрет по защищённому каналу (MDM, система управления конфигурацией, защищённая шара или система развёртывания), а не из публичного URL или исходного кода.
3. Агент обменивает секрет регистрации на уникальные постоянные учётные данные. Master хранит только хеш токена; сам токен возвращается один раз и сохраняется локально с ограниченными правами.
4. В зависимости от политики новый агент либо автоматически одобряется по строго заданным правилам, либо ожидает подтверждения администратора. Коды регистрации должны истекать, иметь лимит применений и отзываться.
5. Агент устанавливается как служба Windows или systemd-служба с автозапуском, перезапуском при сбое, по возможности отдельной учётной записью с минимальными правами и централизованными логами.

## Фоновый запуск текущего агента

Пока встроенный установщик службы не добавлен, используйте штатный менеджер служб или систему развёртывания организации. В Linux systemd unit должен запускать собранный бинарник с фиксированной рабочей директорией, ограниченными правами доступа к конфигурации, политикой `restart-on-failure` и отдельной учётной записью. В Windows используйте утверждённую обёртку службы или упакуйте агент как нативную службу. Защитите `configs/agent.yaml`; не помещайте рабочие токены в Git, публичные аргументы установщика, скриншоты или логи. Интерактивные установщики проверяйте отдельно: фоновая служба может не иметь доступа к рабочему столу вошедшего пользователя.

## Текущие ограничения и план развития

- Автоматическая регистрация без предварительно переданного токена агента пока не реализована.
- Встроенная установка службы Windows и systemd unit пока отсутствуют.
- Постоянный сбор телеметрии, пересылка событий, правила оповещений и уведомления администратора не реализованы; метрики запрашиваются по требованию.
- Будущий процесс регистрации должен использовать одноразовые bootstrap-секреты с ограниченным сроком действия, отдельную идентичность агента, контроль одобрения, ограничение частоты запросов, TLS/WSS и аудит.

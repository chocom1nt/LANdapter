**LANdapter** – клиент-серверная система для централизованной удалённой установки драйверов и программного обеспечения в локальной сети.

Система состоит из **Master** (сервер) и **Agent** (клиентские машины). Master управляет подключёнными агентами, раздаёт файлы и отслеживает результаты установок. Агенты получают команды через WebSocket, скачивают пакеты и запускают установщики с учётом выбранного режима.

Проект создан для упрощения администрирования рабочих станций в офисных и промышленных сетях, где требуется оперативно обновлять драйверы или устанавливать приложения на десятки и сотни машин.

## Возможности

- **Централизованное управление** – все агенты подключаются к единому мастер-серверу.
- **Удалённая установка** – передача файлов (EXE, MSI, INF, DEB, RUN, TAR) на агенты и запуск с нужными параметрами.
- **Режимы установщика** – тихий, базовый UI и интерактивный UI там, где формат это поддерживает. Для MSI используются `/qn`, `/qb` и полный UI; поведение EXE и Linux-пакетов зависит от самого установщика.
- **Инвентарь устройств** – агент сообщает об устройствах Windows Plug and Play или Linux PCI/USB, поставщиках и версиях драйверов, кодах ошибок и возможном отсутствии привязки драйвера как диагностической подсказке.
- **История и отчёты** – каждое задание сохраняется в базе данных вместе со снимками состояния системы до и после установки.
- **Точки восстановления** – автоматическое создание точки восстановления перед установкой на Windows.
- **Веб-интерфейс** – панель React с тёмной темой, инвентарём клиентов и устройств, графиками доступности и распределения ОС, а также текущими метриками CPU/RAM/uptime онлайн-агента. Историческое хранение временных рядов пока не включено.
- **Групповые политики и планировщик** – набор загруженных пакетов, фильтр ОС, немедленный запуск и повторный запуск по интервалу. Расписание повторно запускает установку, поэтому сначала проверяйте пакет на тестовом клиенте.
- **Терминальный интерфейс (`lndp`)** – цветной TUI с четырьмя вкладками, справкой по `?`/`F1`, поиском и выбором клиентов, диагностикой устройств, мониторингом CPU/RAM/uptime и двухпанельным файловым менеджером для загрузки и установки пакетов.
- **Гибкая конфигурация** – YAML-файлы, поддержка переменных окружения.
- **Кроссплатформенность** – Master и Agent поддерживают Windows и Linux. Выполнение установок на macOS пока не поддерживается.

## Быстрый старт

### Требования

- Docker Engine с плагином Docker Compose
- Node.js 18+ для веб-интерфейса
- Go 1.26.4+ — только если собираете или запускаете Go-бинарники вне Docker

### Подготовка и запуск

В корне репозитория выполните:

```bash
make quickstart
```

`make quickstart` создаёт или исправляет `.env`, копирует примеры конфигурации при отсутствии локальных файлов, устанавливает frontend-зависимости и запускает PostgreSQL с Master. При **новом Docker volume** PostgreSQL автоматически создаёт схему по SQL-миграциям. Для существующей базы init-скрипты повторно не запускаются.

Установите и запустите веб-интерфейс в отдельных терминалах:

```bash
make run-frontend
```

Откройте `http://localhost:3000`, выполните `make copy-token` и один раз вставьте скопированный admin token в разделе **Настройки**. Браузер хранит его только в текущем сеансе. `lndp` читает токен из `.env` автоматически — вручную экспортировать переменную для TUI не нужно.

Чтобы собрать и запустить TUI:

```bash
make build-tui
make run-tui
```

В настройках выпустите отдельные учётные данные для каждого Agent и сохраните их в `configs/agent.yaml`, затем выполните `make run-agent`.

Для существующих установок и ручной настройки PostgreSQL используйте [руководство по установке](INSTALL.md). После обновления существующей БД примените миграцию политик/расписаний: `make migrate-apply NAME=007_policies_schedules`. См. [руководство по устройствам, политикам и планировщику](DEVICES-POLICIES-SCHEDULES.md). Не выполняйте `docker compose down -v`, если не собираетесь удалить том базы данных.

## Сборка из исходников

### Бинарники Go

Соберите мастер и агента:

```bash
make build
```

Либо вручную:

```bash
go build -o bin/master cmd/master/main.go
go build -o bin/agent cmd/agent/main.go
```

### Фронтенд

Соберите React-приложение:

```bash
cd web
npm run build
```

Готовая статика появится в `web/dist/`.

### Docker-образы

Корневой `Dockerfile` собирает образ Master (в него также включён бинарник агента), а `Dockerfile.agent` — отдельный образ Agent:

```bash
docker build -t landapter-master .
docker build -f Dockerfile.agent -t landapter-agent .
```

`make setup` создаёт локальные секреты и конфигурации, а `make up` запускает PostgreSQL и Master. На новой Docker volume схема БД инициализируется автоматически. Веб-интерфейс и агенты запускаются отдельно; подробности — в [руководстве по установке](INSTALL.md).

## Структура проекта

```text
LANdapter/
├── cmd/                  # Точки входа
│   ├── master/
│   └── agent/
├── internal/             # Внутренние пакеты
│   ├── common/           # Общие структуры, логирование, конфиг
│   ├── master/           # Логика мастера (HTTP, WebSocket, хендлеры)
│   └── agent/            # Логика агента (подключение, установка)
├── storage/              # Слой данных (интерфейс + PostgreSQL)
├── migrations/           # SQL-миграции
├── web/                  # React-фронтенд
├── docs/                 # Документация
├── configs/              # Примеры конфигурационных файлов
├── uploads/              # Папка для загруженных файлов (создаётся автоматически)
├── docker-compose.yml
├── makefile
├── go.mod
└── README.md
```

## Тестирование

Запуск юнит-тестов:

```bash
make test
```

Проверка production-сборки фронтенда:

```bash
cd web && npm ci && npm run build
```

На данный момент в репозитории нет отдельного набора интеграционных тестов с настоящей БД. Цель `make test-integration` зарезервирована и сообщит об этом до появления таких тестов. Перед публикацией выполните проверки из [чек-листа релиза](RELEASE-CHECKLIST.md).

```bash

```

## Текущие ограничения и планы развития

- Сейчас политики выбирают клиентов по подстроке ОС; постоянные группы и теги клиентов ещё не реализованы.
- Панель показывает текущие метрики и графики распределения, но не сохраняет исторические временные ряды.
- Инвентаризация выдаёт диагностические подсказки, но не скачивает, не проверяет подписи и не устанавливает драйверы автоматически.
- Планировщик повторно запускает установку пакетов. Используйте доверенные идемпотентные установщики и сначала проверяйте политику на тестовом клиенте.
- Интеграция с AD/LDAP, новые форматы пакетов, расширенная история заданий и поиск драйверов у производителей остаются будущими задачами.

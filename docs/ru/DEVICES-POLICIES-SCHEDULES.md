# Инвентарь устройств, политики и планировщик

## Инвентарь устройств

В веб-панели откройте **Устройства**, выберите клиента и запросите инвентарь. Для Windows агент получает список присутствующих Plug and Play устройств и свойства поставщика/версии драйвера/кода проблемы. Код 28 отмечается как отсутствие установленного драйвера; другие ненулевые коды показываются как общая проблема устройства. Для Linux агент перечисляет устройства PCI/USB и проверяет наличие привязки `driver` в `/sys`.

Диагностика не скачивает и не устанавливает драйверы автоматически. Для USB на Linux и некоторых виртуальных устройств отсутствие отдельной привязки в sysfs может быть ожидаемым; рассматривайте отметки как подсказки, а не окончательный вывод.

## Групповые политики

Страница **Политики и расписание** позволяет создать декларативную политику установки из уже загруженных пакетов, задать необязательный фильтр ОС и режим установки. Фильтр ОС на этой версии — подстрока без учёта регистра в строке ОС клиента, а не полноценная система групп/тегов.

## Планировщик

Расписание задаёт интервал от 5 минут до 30 дней. При наступлении срока Master выбирает **онлайн** клиентов, подходящих под фильтр ОС, и отправляет им пакетную установку. Следующий запуск рассчитывается от фактического прохода планировщика; сам планировщик проверяет очередь примерно раз в 30 секунд. Если в момент запуска подходящих онлайн-клиентов нет или отправка завершилась ошибкой, расписание всё равно переносится на следующий интервал — проверьте журналы Master.

> **Внимание:** расписание повторно устанавливает выбранные пакеты при каждом срабатывании. Начинайте с тестового клиента и тестового установщика. Для производственных развёртываний используйте только проверенные, идемпотентные пакеты.

## Миграция БД

В существующей базе данных примените только новую миграцию (не запускайте повторно все миграции поверх уже созданной схемы):

```sh
make migrate-apply NAME=007_policies_schedules
```

Для чистой БД Docker применит миграцию при первой инициализации volume. Добавление SQL-файла в `docker-entrypoint-initdb.d` не применяет его повторно к уже существующему `postgres_data`.
